# jshack.me

A multiplayer hacking simulation you play entirely from a retro terminal in the browser. Every
machine, network and password in it is generated by the game. It touches no real system, network
or account.

**Play it at [jshack.me](https://jshack.me).** Press **NEW GAME**, pick a hostname, username and
root password, then type `help`.

## What you do in the game

You start at your own workstation with only the WiFi in range. From there:

- **Break in.** Crack a WiFi network and join it, scan the machines on it, and get into them
  through weak passwords, careless services and published vulnerabilities in the software they
  run.
- **Go further.** Beyond the first network lies Harrow Valley: eleven towns of homes, shops,
  offices and public websites, reached through gateways, the in-game DNS and a search engine.
- **Take work.** Contractor boards post paid jobs against other people's machines, and clients
  pay in the game's own currency.
- **Watch your back.** Players who join the same network share it, so they can reach your
  workstation as easily as you can reach theirs. A machine destroyed by another player stays
  destroyed.

There is no walkthrough. Your home folder has a short `README`, and the world has a site that
teaches its tools. Working out what to do next is the game. LLM agents are welcome to play too:
[jshack.me/llms.txt](https://jshack.me/llms.txt) explains how to drive the terminal.

## How it is built

| Part   | What it is                                                                                      |
| ------ | ----------------------------------------------------------------------------------------------- |
| Client | Solid.js, Vite and Tailwind, in strict TypeScript. The game itself runs in the browser.         |
| Server | Vercel Functions in `api/`, which guard the state players share. Supabase Postgres stores it.   |
| World  | Generated from code. The database holds only what players changed, not the world itself.        |
| Player | An Ed25519 keypair kept in the browser. There are no accounts; every server request is signed.  |
| Tests  | Vitest with jsdom and `@solidjs/testing-library`, Stryker for mutation testing, and wire-checks |

The wire-checks are the `scripts/test*.ts` files, run against a live `vercel dev` and a local
Supabase. They prove the server and database together.

```
src/
  core/       pure TypeScript, no framework, shared by the client and the server
  adapters/   signed fetch clients for api/, and the cross-tab BroadcastChannel
  ui/         Solid components and screens
api/          Vercel Functions: network, patches, sessions, wallet
scripts/      build checks, wire-checks and operator scripts
supabase/     migrations and local stack config
docs/         the maintainer's handbook and as-built architecture
```

## Run it locally

You need Node.js and npm, Docker Desktop (for the local Supabase) and the Vercel CLI
(`npm i -g vercel`).

> **You also need the password pools.** The world draws every in-game password from pools that the
> repository does not contain, which keeps them away from players. `npm run encode`, and every
> script that runs it first, stops with `JSHACK_SECRETS: not set` until they are in your env file.
> They are pulled from the project's Vercel environment, so a clone without access to that project
> cannot build or run the game.

```bash
npm install
npx supabase start            # local Postgres in Docker; applies supabase/migrations/
npx supabase status -o env    # prints the local keys for .env.development.local
# write .env.development.local: the Supabase keys plus JSHACK_SECRETS (see the handbook, chapter 2)
npm run encode                # generates the git-ignored pool files in src/core/secrets/
npm run vercel:dev            # the game and the api/ functions on http://localhost:3100
```

Open `http://localhost:3100` and start a new game. The version in the boot banner should match
`package.json`; if it does not, an old server is still running.
[Chapter 2 of the handbook](./docs/handbook/02-local-development.md) has the exact env file, a
health check for the API and how to start over with a fresh player or database.

## Commands

| Command                 | What it does                                                                                                 |
| ----------------------- | ------------------------------------------------------------------------------------------------------------ |
| `npm run vercel:dev`    | The game and the `api/` functions on port 3100.                                                              |
| `npm run dev`           | Vite alone. The game boots, but every server-backed command fails.                                           |
| `npm run typecheck`     | `tsc -b` over `src/`, `api/` and `scripts/`. A plain `tsc --noEmit` checks nothing.                          |
| `npm run lint`          | ESLint, including the rule that every relative import ends in `.js`.                                         |
| `npm run test:run`      | The whole Vitest suite once.                                                                                 |
| `npm run build`         | Type check and production build, then the secrets check and the world budgets (bundle size, box build time). |
| `npm run test:mutation` | Stryker. A whole-suite run does not finish; scope it to the files you changed.                               |

How to run one wire-check, and how to scope a mutation run, are in
[chapter 11](./docs/handbook/11-testing-and-quality.md).

## Deployment

Vercel builds the repository root. `main` deploys to production against the `jshack-prod`
Supabase project, and every other branch gets a preview deployment against `jshack-dev`. Schema
changes are Supabase migrations in `supabase/migrations/`. The details are in
[chapter 12](./docs/handbook/12-build-deploy-operate.md).
